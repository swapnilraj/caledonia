* DONE Deleting occurrence of all-day recurring event writes wrong EXDATE
  Two issues when deleting a single occurrence of a =VALUE=DATE= recurring event:
  1. *Wrong date*: the occurrence date is being converted through UTC, so e.g.
     April 12 midnight BST (UTC+1) becomes April 11 23:00 UTC, truncated to
     April 11. The EXDATE ends up one day off, so the occurrence isn't actually
     excluded and an unrelated date is silently suppressed.
  2. *Missing VALUE=DATE*: the EXDATE is written as =EXDATE:20260411= instead of
     =EXDATE;VALUE=DATE:20260411=. Without =VALUE=DATE=, the parser treats it as
     a datetime, fails with =check_date_datetime=, and the whole file becomes
     unparseable.
* DONE Occurrence mutations carry typed query identity
  Query results now return the exact RFC 3339 =occurrence_start= together with
  the explicit =occurrence_timezone= and typed =recurrence_id_value=. Clients
  forward that pair for edit/delete instead of manually calculating an offset
  from a presentation time. Floating, TZID, UTC, and VALUE=DATE occurrences
  therefore preserve their local RECURRENCE-ID/EXDATE semantics even when the
  client and server process timezones differ.
* DONE =list --type todo= returns nothing because of datetime bounds
  Todos typically have no date, so they're excluded by =list='s default date range filter.
  You have to use =search --type todo= instead, which is confusing.
  Either =list= should skip date bounds for todos, or hint the user.
